# Kubernetes deployment

## TL;DR

Deployment is **manual**, after configuring your site; no controller auto-syncs these files:

```sh
kubectl apply -k k8s
```

## Requirements

- Kubernetes 1.29+ with the `SidecarContainers` feature enabled (default from 1.29), kubectl with Kustomize, a default storage class and an nginx ingress controller.
- A CNI that enforces NetworkPolicy. The pod satisfies the restricted Pod Security profile.
- Your existing OIDC provider and a trusted TLS certificate for the application hostname.

No application operator or CRD is required. cert-manager and its issuer are optional if you use them to provision TLS. Rancher project assignment and inherited policies remain cluster prerequisites.

## Configuration layout

This directory is one base; no environment overlays ship with it. A site overlay changes the namespace/project labels, issuer/client/group settings, hostname/certificate and storage class. Keep site-specific values and secrets in your deployment repository. The stable `app: neo4j-sso` selectors are intentional; changing selectors on an existing Deployment requires recreation.

## Deliberately manual

You control deploy/sync timing, namespace project assignment, IdP registration and Secret/TLS provisioning. The base does not install a certificate issuer, secret store or GitOps controller, or grant an ArgoCD AppProject access to a new namespace. These are estate-level responsibilities. Secret rotation needs an explicit rollout; database backups remain your responsibility.

## Config

Site configuration lives in `oauth2-proxy.env`, `ingress.yaml`, `storage.yaml` and the untracked Secret. Keep this directory as your deployment copy or create a Kustomize overlay.

| Req | Name | Purpose |
|---|---|---|
| Required | `oauth2-proxy.env` | Replace example issuer, callback URL, Bolt address, allowed groups/email domains and ingress source CIDRs |
| Required | `ingress.yaml` | Replace both hostname entries and select your ingress class |
| Required | `neo4j-sso-tls` Secret | Provide a TLS keypair, or add your cert-manager issuer annotation to the Ingress |
| Required | `neo4j-sso-oidc` Secret | Provide client secret and random cookie key; `oidc-secret.example.env` lists the required keys |
| Optional | `storage.yaml` | Set a storage class if your cluster has no default; adjust the 5Gi request before provisioning |

Register the exact configured callback URI at your IdP. Set the Bolt address to the public application hostname and port 443. The browser and the application pod must resolve and reach the issuer. If your IdP uses a private CA, mount its CA bundle into the SSO container and set `OAUTH2_PROXY_PROVIDER_CA_FILES` to its path. Do not set an insecure TLS flag.

## Minimum configuration

Configure the site values in the files above. Copy `k8s/oidc-secret.example.env` to a private, gitignored `oidc.secret.env`; fill its two values. A public PKCE client uses `unused-public-client` as the client-secret placeholder. Generate the cookie value locally with `python3 -c 'import secrets; print(secrets.token_urlsafe(32))'`.

Confirm `kubectl config current-context` points at your intended cluster. Create the namespace and client Secret:

```sh
kubectl apply -f k8s/namespace.yaml
kubectl -n neo4j-sso create secret generic neo4j-sso-oidc --from-env-file=oidc.secret.env
```

Provision `neo4j-sso-tls` in the same namespace using your normal certificate process before exposing the service. If Rancher assigns namespaces to projects, assign this namespace to your intended project and check its inherited network policies.

## Ports and volumes

Only the SSO listener is served by the ClusterIP Service and HTTPS Ingress. Neo4j listens on `127.0.0.1:7474` and `127.0.0.1:7687` inside the pod; nginx listens on `127.0.0.1:8080`. There is no raw database Service, NodePort or load balancer.

`neo4j-sso-data` is a 5Gi ReadWriteOnce PVC mounted at `/data`. The single-replica Deployment uses `Recreate` so an update does not compete for that volume. Pod recreation retains data. Do not delete the namespace or PVC unless you intend to remove the test database; volume deletion behavior also depends on the storage class reclaim policy.

All image filesystems are read-only. A short init container copies the image's vendor configuration into a bounded writable volume before startup. Config, logs, PID files and temporary files use bounded `emptyDir` volumes and disappear on pod recreation; only `/data` persists. Collect logs externally if you need retention. The dedicated ServiceAccount has no application RBAC grants, and token automount is disabled.

## Preconditions

- DNS resolves the application hostname to your ingress, and the certificate matches that hostname.
- Ingress forwards WebSocket upgrades, with the configured one-hour proxy timeout.
- Project/namespace policies permit DNS, issuer access and ingress traffic to port 4180.

## Behaviour

Configuration changes generated by Kustomize produce new ConfigMap names and roll the pod. A changed Secret needs `kubectl -n neo4j-sso rollout restart deployment/neo4j-sso`. Keep the cookie key stable to preserve sessions.

Neo4j receives only its explicit environment variables: `enableServiceLinks: false` prevents Kubernetes' generated `NEO4J_*` Service variables from being parsed as invalid database settings.

Neo4j probes have an explicit ten-second timeout; gateway readiness checks the local request path, with a five-second budget. SSO liveness checks only its in-process ping, with a longer failure window than readiness. Neo4j and nginx deliberately have no dependency-driven liveness probe: crashes restart normally, while sustained not-ready states need investigation.

The pod allows 90 seconds for termination. Neo4j's preStop waits ten seconds for ingress endpoint removal, then the database stops. Native sidecars remain alive until the database exits and terminate in reverse order: SSO, then nginx. This is bounded shutdown, not uninterrupted availability: updates disconnect long-lived WebSockets and clients must reconnect. Revision history retains three versions; CPU limits retain the existing policy.

The admission and permission limits in the root [README](../README.md#behaviour) apply here. Keep native database ports private even if you replace the pod layout.

## Expected result

`kubectl -n neo4j-sso rollout status deployment/neo4j-sso` reports success and all three containers are ready. An anonymous visit redirects to your IdP; an admitted account reaches Browser. Choose **No authentication** if Browser asks for database credentials, using `bolt+s://neo4j.example.internal:443` after substituting your hostname.

For a disposable Keycloak deployment with `demo` and `outsider` test accounts sharing a test password, set `TEST_PASSWORD` in your shell and run the root `tests/check_sso.py` with `--url`, `--issuer` and, if necessary, `--ca-file`. The script never disables TLS verification. Do not use a production account for that test.

Run `bash tests/check_k8s.sh` with the CI-pinned validation tools to check rendering warnings, Kubernetes 1.29 schemas, semantic/readiness lint, pod hardening/token-mount checks and deprecated APIs through 1.36.4. Before applying a site overlay, run `kubectl diff` and `kubectl apply --dry-run=server` against its exact rendered resources. Offline gates do not establish your cluster's admission policy or IdP connectivity.
